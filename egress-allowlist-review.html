This replaces the earlier four-finding assessment. The earlier DNS defect label and suggestion that child behavior was exceptional to this feature were overstated. The findings below distinguish observed behavior from the policy choices that determine whether it needs changing.

DNS trustAccepted behavior

Allowed peers may also answer DNS

Under the intended model, allowing an IP also permits using it as a DNS server. That is not a defect.

The additional consequence is that a permitted peer’s matching DNS response for an allowed name can authorize other destination IPs. The existing reproduction demonstrated this transitive authority. It did not establish a violation of the intended policy.

Recommendation. No separate resolver allowlist is needed for that model. A brief documentation sentence can make the trust explicit: any allowed destination that serves DNS can supply addresses for allowed domain names. The existing text refers only to “the configured resolver”. See query tracking and the trust-model text.

Configuration contractCorrect scope

Child restrictions are ignored, as shared network settings are

Confirmed with real runsc root and child containers. A child-only restriction does not install a filter, and a narrower child restriction does not replace the root’s policy.

The test started an HTTP server at 192.0.2.1:18080, created a sandbox with a veth-backed network namespace, then launched a child with actual OCI annotations. Both containers made real TCP connections.

StartSubcontainer sends child config without repeating network setup. The new filter is constructed once and shared across the sandbox’s links.

For Kubernetes, containerd’s CRI configuration documentation states that configured pod_annotations are forwarded to both sandbox and container OCI specs. The ordinary Pod-annotation path therefore reaches the root and works. Child-only container_annotations are a different case.

Recommended fix approach

Use the existing sandbox model. Change “per-container” to “per-sandbox”. State that policy must be supplied when creating the root sandbox or pause container, that all children inherit it, and that learned DNS addresses are shared. Add a multi-container integration test for inheritance, including an unannotated child.

Optional guard. If successful startup with an ineffective explicit child request is unacceptable, add a targeted check for egress annotations against the installed sandbox policy. Accept repeated equivalent Pod annotations and children without an explicit policy. Compare normalized effective policies, not the entire config struct. This would be new validation for this feature, not an existing blanket gVisor convention.

Do not intersect the live shared policy when a child starts. That changes siblings’ access, makes behavior depend on startup order, and raises questions about previously learned DNS state. Independent child policies require a separate design with container identity at the enforcement point.

Receive-path correctnessFix verified

Pass the NIC’s checksum decision into the DNS learner

The same offloaded DNS reply reaches a real UDP socket but is rejected by the learner. Passing link capability context fixes that mismatch.

The filter runs before the NIC assigns RXChecksumValidated. Its byte-only clone also starts with that flag unset. Reading the clone flag therefore requests software checksums even when the receive link advertises checksum offload. Fully checksummed replies are unaffected.

Smallest consistent change. Compute the boolean from the endpoint’s capabilities and pass it to snoopInbound. Use it for the IPv4 header and UDP checksum checks. This matches the NIC’s existing decision. Copying the incoming packet flag alone is insufficient, and OR-ing it with capabilities would trust metadata that the NIC overwrites on a non-offload link.

IPv6 deployment limitationDefer

Handle non-link-local gateways only if deployments need them

The reproduced failure is conditional. I would not add next-hop policy machinery for it in this change without a concrete deployment requirement.

It affects an unlisted global or ULA IPv6 next hop. The current exemption permits link-local NDP, but later unicast neighbor probes may target the gateway’s global or ULA address and be dropped. IPv4 and the tested link-local gateway path are unaffected. This was reproduced through netstack’s IPv6 resolver, not a live deployment.

Recommendation. Document that non-link-local IPv6 gateway addresses may need explicit allowance. If granting application access to the gateway is undesirable, keep that topology unsupported for now. Revisit a narrowly validated NS/NA exemption only when this topology is required.

Sources: current exemption, neighbor probes, unicast solicitation, and RFC 4861 §7.3.

Design and gVisor conventions

Keep the link-layer enforcement design

Socket or raw packet→NIC + qdisc→Egress filter→Sniffer→fdbased / XDP

The enforcement point covers the raw and packet-socket routes inspected. Shared parsing, immutable static rules, bounded DNS tables, and one filter across NICs fit the intended sandbox model. The synthetic TCP reset path was checked with real IPv4 and IPv6 TCP endpoints, and both returned connection refused promptly.

The implementation uses existing nested endpoints, packet ownership, clocks, and synchronization abstractions. Selected static checks and the complete runsc build pass. No coding-style issue or case for a broader rewrite was demonstrated. The significant implementation correction is carrying the receive checksum contract into DNS learning.

The documented choices remain design tradeoffs: IP-level authorization includes shared hosts, learned addresses persist until sandbox state is lost, learning is bounded and UDP-only, and replies to unlisted inbound peers are dropped. This review does not treat those documented choices as additional defects.
